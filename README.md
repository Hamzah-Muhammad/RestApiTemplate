A small, complete example REST API — meant to be forked and repointed at whatever resource you actually need, not run as-is. It's built as a **task tracker** (users → projects → tasks) purely as a stand-in domain; the point is everything *around* the CRUD: JWT auth, ownership-scoped access control, migrations, pagination, tests, containerization, and CI, wired together the way a real service would ship them.

**Stack:** Python + FastAPI, SQLAlchemy ORM with Alembic migrations (SQLite for local dev, Postgres in Docker/production — one env var swaps between them), JWT bearer auth (`pyjwt` + `bcrypt`), pytest for tests, Docker + docker-compose for containerization, GitHub Actions for CI. No external services to connect to — everything runs locally out of the box.

Interactive API docs (Swagger UI) are auto-generated by FastAPI at `/docs` once it's running.

## What's in the box

- **JWT auth** — register/login with bcrypt-hashed passwords, bearer-token-protected routes
- **Ownership-scoped access control** — two related resources (`Project` → `Task`) with foreign keys, cascade deletes, and per-user access control: you can only ever read/write your own data, enforced on every route, not just in the UI. A 404, not a 403, for someone else's resource — doesn't leak that it exists.
- **Pagination, filtering, sorting** — `limit`/`offset` on every list endpoint, `status` filter and `sort_by`/`sort_dir` on tasks (sort fields whitelisted, never interpolated)
- **Versioned routes + one error envelope** — everything under `/v1`; every error is `{"error": {"code", "message"}}` — see [Conventions](#conventions)
- **Alembic migrations** — schema is versioned, not `create_all()`'d on boot
- **SQLite for local dev, Postgres for anything real** — swap by changing one env var; docker-compose runs the Postgres path
- **27 pytest tests** — auth, ownership isolation, error envelope, expired/garbage tokens, pagination clamping, query validation — against an isolated in-memory DB, no test pollution between runs
- **Docker + docker-compose** — `docker compose up` gets you the API + Postgres with migrations applied automatically; the image runs as a non-root user with a readiness `HEALTHCHECK`
- **GitHub Actions CI** — ruff lint + pytest on every push/PR

## Quick start

Two ways to run it — pick whichever matches what you have installed. Both end up serving the same API on the same routes; only the database underneath differs.

### Local, SQLite, no Docker

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS/Linux

pip install -r requirements-dev.txt
cp .env.example .env            # defaults to SQLite, fine as-is for local dev

alembic upgrade head
uvicorn app.main:app --reload
```

Open http://127.0.0.1:8000/docs and try it interactively (Swagger's "Authorize" button handles the bearer token for you), or drive it from the command line — see [Walkthrough](#walkthrough-register-log-in-use-it) below.

### Docker Compose, Postgres

```bash
docker compose up --build
```

This builds the API image, starts Postgres, waits for its healthcheck, then runs `alembic upgrade head` before starting uvicorn. API is on http://localhost:8000.

## Running the tests

```bash
pytest -v
```

Tests run against a fresh in-memory SQLite database per test (via a `get_db` dependency override in `tests/conftest.py`) — nothing touches your real `.env` database or requires Postgres to be running.

## API overview

| Method | Path | Auth | What it does |
|---|---|---|---|
| POST | `/v1/auth/register` | — | Create a user |
| POST | `/v1/auth/login` | — | Exchange email+password for a JWT (OAuth2 password flow) |
| GET | `/v1/auth/me` | ✓ | Current user's profile |
| POST | `/v1/projects` | ✓ | Create a project |
| GET | `/v1/projects?limit=&offset=` | ✓ | List your projects, paginated |
| GET / PATCH / DELETE | `/v1/projects/{id}` | ✓ | Read/update/delete a project you own |
| POST | `/v1/projects/{id}/tasks` | ✓ | Create a task under a project you own |
| GET | `/v1/projects/{id}/tasks?status=&sort_by=&sort_dir=&limit=&offset=` | ✓ | List a project's tasks, filtered/sorted/paginated |
| GET / PATCH / DELETE | `/v1/tasks/{id}` | ✓ | Read/update/delete a task in a project you own |
| GET | `/health` | — | Liveness: process is up |
| GET | `/health/ready` | — | Readiness: database reachable (503 if not) — what the Docker `HEALTHCHECK` polls |

Full request/response schemas are in `/docs` — every route is typed end to end with Pydantic models, so the OpenAPI spec is always accurate, never hand-maintained.

### Conventions

- **Versioned paths.** Every resource route lives under `/v1`; a breaking change ships as `/v2` alongside it instead of breaking existing clients. Health endpoints stay unversioned — load balancers shouldn't have to track API versions.
- **Status codes mean what they say.** `201` on create, `204` (empty body) on delete, `409` on a duplicate email, `401` + `WWW-Authenticate: Bearer` on a missing/bad/expired token, `422` on validation, `404` for anything you don't own.
- **One error shape.** Every non-2xx response is the same envelope, so clients handle errors in one place:

  ```json
  {"error": {"code": "not_found", "message": "Project not found"}}
  ```

  Validation failures add a `details` list (`app/core/errors.py`):

  ```json
  {"error": {"code": "validation_error", "message": "Request validation failed",
             "details": [{"field": "email", "message": "value is not a valid email address"}]}}
  ```

- **`PATCH` is a true partial update** — only fields present in the body change; sending `"description": null` clears it, omitting it leaves it alone.
- **Pagination is bounded** — `limit` is clamped to 1–100 and `offset` to ≥ 0 server-side, and every list response echoes `limit`/`offset`/`total` so clients can page without guessing.

## Walkthrough: register, log in, use it

Every command below was run against a live local instance to confirm the exact request/response shown. Start the server first:

```bash
uvicorn app.main:app --reload
```

All examples use `curl`. Swap in `httpie`, Postman, or the `/docs` Swagger UI if you prefer — same requests, same responses. IDs and timestamps will differ on your machine; everything else will match exactly.

**In a hurry — e.g. mid-interview and you just need `GET`-able data on screen?** Skip straight to [Pre-seeded demo data](#pre-seeded-demo-data) below and come back to this walkthrough later.

### 1. Register a user

```bash
curl -X POST http://127.0.0.1:8000/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "full_name": "Your Name", "password": "supersecret1"}'
```

```json
{"id":1,"email":"you@example.com","full_name":"Your Name","created_at":"2026-08-11T09:24:39.709170"}
```

### 2. Log in to get a JWT

`/v1/auth/login` is an OAuth2 password flow, so the body is form-encoded (`username`/`password`), not JSON:

```bash
curl -X POST http://127.0.0.1:8000/v1/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=you@example.com&password=supersecret1"
```

```json
{"access_token":"eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...","token_type":"bearer"}
```

Copy the `access_token` value — every authenticated request below sends it as `Authorization: Bearer <JWT>`.

### 3. Call authenticated endpoints

```bash
# Your own profile
curl http://127.0.0.1:8000/v1/auth/me \
  -H "Authorization: Bearer <JWT>"
```
```json
{"id":1,"email":"you@example.com","full_name":"Your Name","created_at":"2026-08-11T09:24:39.709170"}
```

```bash
# Create a project
curl -X POST http://127.0.0.1:8000/v1/projects \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"name": "Demo project"}'
```
```json
{"id":1,"name":"Demo project","description":null,"owner_id":1,"created_at":"2026-08-11T09:24:40.200456"}
```

```bash
# Create a task under it (project id from the response above — 1 on a fresh DB)
curl -X POST http://127.0.0.1:8000/v1/projects/1/tasks \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"title": "First task"}'
```
```json
{"id":1,"title":"First task","description":null,"status":"todo","due_date":null,"project_id":1,"created_at":"2026-08-11T09:24:40.255678"}
```

### 4. See the ownership check in action

Register a second user, log in as them, and try to touch the first user's project:

```bash
curl -X POST http://127.0.0.1:8000/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "someone-else@example.com", "full_name": "Someone Else", "password": "supersecret1"}'

curl -X POST http://127.0.0.1:8000/v1/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=someone-else@example.com&password=supersecret1"
# use this second token below as <OTHER_JWT>

curl http://127.0.0.1:8000/v1/projects/1 -H "Authorization: Bearer <OTHER_JWT>"
# 404 Not Found — same response as if the project didn't exist at all,
# so a client can't distinguish "not yours" from "doesn't exist"
```

## Pre-seeded demo data

For when you need `GET`-able data on screen without typing out the walkthrough above first — e.g. mid-interview. Run once, against a migrated dev DB:

```bash
python -m scripts.seed_demo_data
```
```text
Seeded:
  user   dana@example.com  (2 projects, 5 tasks)
  user   marcus@example.com  (1 project, 2 tasks)
All passwords: password123
```

It's idempotent — every user is looked up by email first, so running it again (e.g. after restarting with a fresh `app.db`) just confirms the same state instead of erroring on a duplicate. Log in as either user to hit `/v1/projects` and `/v1/projects/{id}/tasks` with real, varied data — different `status` values and `due_date`s, so `?status=` and `?sort_by=&sort_dir=` have something to actually filter/sort. Log in as the other one to see the ownership check return an empty list / 404s for the first user's data.

## Adapting this template for a real project

This is meant to be forked, not extended in place as a task tracker. To repoint it at a different domain:

1. **Rename the resources.** `Project` and `Task` in `app/models/`, `app/schemas/`, `app/crud/`, `app/routers/` are the two-resource, one-to-many pattern (a parent that owns a user, a child that belongs to the parent). Swap the field names and add/remove fields for your actual domain — the ownership-check pattern in `app/routers/projects.py::get_owned_project_or_404` and `app/routers/tasks.py::_get_owned_task_or_404` is the part worth keeping as-is.
2. **Regenerate the migration.** After changing models, delete the SQLite dev DB (`app.db`) and the existing revision in `alembic/versions/`, then run `alembic revision --autogenerate -m "initial schema"` again. Never hand-edit an already-applied migration — add a new one.
3. **Update `docker-compose.yml`'s `POSTGRES_DB` name and the `DATABASE_URL`** to match your project's name.
4. **Extend `Pagination` in `app/deps.py`** if you need cursor-based pagination instead of offset-based — offset pagination is simple but gets slow on very large tables; that's a real tradeoff being made here, not an oversight.
5. **`SECRET_KEY`** in `.env` must be a real random value in any deployed environment — generate one with `python -c "import secrets; print(secrets.token_hex(32))"`. The one in `.env.example` is a placeholder and will fail loudly if you deploy with it (add that check yourself if you want a hard guardrail).

## Project layout

```
app/
  core/
    config.py        Settings (pydantic-settings, reads .env)
    errors.py        Exception handlers -> the one JSON error envelope
    security.py       Password hashing, JWT encode/decode
  models/              SQLAlchemy ORM models (User, Project, Task)
  schemas/             Pydantic request/response models
  crud/                DB access functions, one module per resource
  routers/             FastAPI route handlers (auth, projects, tasks)
  deps.py              get_current_user, Pagination
  db.py                Engine/session setup
  main.py              App instance, /v1 router wiring, health + readiness
alembic/               Migration environment + versions
scripts/
  seed_demo_data.py    Populates users/projects/tasks for demos - see above
tests/                 pytest suite (conftest has the DB-override + auth fixture)
```
